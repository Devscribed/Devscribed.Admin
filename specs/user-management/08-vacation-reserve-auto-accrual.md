# 08 — Vacation Reserve & Auto-Accrual

## Summary

The vacation reserve is a financial ledger that tracks how much money has been set aside to fund a member's paid vacation. The system **automatically generates monthly credit transactions** on the 1st of each month based on the previous month's expected billing, using the financial settings snapshot (spec 07) that was in effect during the billing month. The reserve balance determines how many vacation days a member has available. Unused balances expire at year-end. This spec covers the ledger, the auto-accrual engine, the balance calculation, and the transactions view on the Vacation tab. Vacation requests (submitting, reviewing, cancelling) are covered in spec 09.

**Depends on:** Spec 07 — MemberFinancials and MemberFinancialsSnapshot must exist for a member before credits can accrue.

## Actors & Preconditions

- **Actors:** The auto-accrual job runs as a **system process** (no human actor). `admin` and `manager` view the transactions table and balance on the Vacation tab. `user` views their own balance (days only).
- **Preconditions:** MemberFinancials must be configured (spec 07). The member must be `active`.

## Functional Requirements

### Vacation Reserve (Ledger)

1. The vacation reserve is tracked as an **append-only transaction ledger** (`VacationReserveTransaction`). The balance is always derived by summing all transactions for a membership within the current calendar year. There is no mutable balance field.
2. Transaction types at this stage:
   - **`credit`** — monthly accrual auto-generated by the system. Amount = `expectedMonthlyBilling × vacationReservePercent / 100`, where `expectedMonthlyBilling = clientHourlyRate × 2080 / 12`. Uses the financials snapshot effective during the billing month.
   - **`expiry`** — year-end zeroing. Amount = negative of the remaining balance, bringing it to zero. Created automatically or by admin/manager action.
3. Transactions are immutable — they cannot be edited or deleted. Corrections are made by adding compensating transactions.

### Automatic Monthly Accrual

4. On the **1st of each month**, the system runs a background job that generates `credit` transactions for all active members with configured financials, covering the **previous month's** expected billing.
5. The credit amount for a full month is:
   ```
   expectedMonthlyBilling = clientHourlyRate × (2080 / 12)
   creditAmount = round(expectedMonthlyBilling × vacationReservePercent / 100, 2)
   ```
   Using the `clientHourlyRate` and `vacationReservePercent` from the **MemberFinancialsSnapshot** that was effective during the billing month (the most recent snapshot with `EffectiveFrom ≤ last day of billing month`).
6. **Pro-rating for new members:** if a member's financials were first configured mid-month (i.e., the `EffectiveFrom` of the earliest snapshot falls within the billing month), the credit is pro-rated:
   ```
   workingDaysInMonth = count of weekdays (Mon–Fri) in the billing month
   workingDaysFromConfig = count of weekdays from EffectiveFrom to end of billing month (inclusive)
   proratedCredit = round(fullMonthCredit × workingDaysFromConfig / workingDaysInMonth, 2)
   ```
7. **No duplicate credits:** the job checks that a credit for the given `BillingPeriodMonth`/`BillingPeriodYear` does not already exist for the membership before creating one. If it exists, the member is skipped.
8. **Members without financials** are silently skipped — no error, no transaction.
9. **Removed members** are skipped — only `active` memberships receive credits.
10. The auto-accrual job is idempotent — running it multiple times for the same month produces the same result (one credit per member per month).

### Manual Accrual Trigger

11. An `admin` can manually trigger the accrual job for a specific billing month via a dedicated API endpoint. This runs the same logic as the background job (requirements 4–10) but for the specified month.
12. The manual trigger is idempotent — if credits for the specified month already exist, those members are skipped.
13. The endpoint returns a summary of the run: total members processed, credits created, and members skipped.
14. Only `admin` can trigger manual accrual. `manager`, `user`, and `viewer` receive `403`.

### Available Vacation Days

15. The available vacation balance is computed as:
    ```
    reserveBalance = SUM(amount) for all transactions of this membership in the current calendar year
    dailySalary = monthlySalary × 12 / 260
    availableDays = floor(reserveBalance / dailySalary)
    ```
16. `availableDays` cannot exceed `vacationDaysPerYear − usedDays`, where `usedDays` is the count of working days across all **approved** requests in the current calendar year (spec 09 introduces requests; until then, `usedDays` = 0). This caps vacation at the configured annual limit even if the reserve has more money.
17. `availableDays` has a floor of `0` — it never shows negative values to the user, even if the reserve is negative due to corrections.

### Year-End Expiry

18. On December 31 (or the first admin/manager action of the new year), any remaining reserve balance from the previous year is zeroed out with an `expiry` transaction. Unused vacation days do not carry over.

> **Implementation note (added during implementation).** The reserve balance is derived as `SUM(amount)` over the transactions whose `CreatedAt` falls in the **current calendar year** (requirement 15), so an unused prior-year balance is already excluded from the live balance the moment the year rolls over — the "unused days do not carry over" behaviour is realised by this year-scoped sum. No standalone expiry-trigger endpoint ships in this spec (none is defined and no test case exercises one); the `expiry` transaction type remains reserved in the enum for a future explicit-zeroing job. When a member's approved requests (spec 09) are added, `usedDays` continues to reference the same current calendar year.

## Flows

### Flow: System auto-generates monthly credits

1. On the 1st of each month, the background job runs.
2. For each active membership with configured financials:
   a. System looks up the MemberFinancialsSnapshot effective during the previous month.
   b. System checks that no credit transaction exists for that billing period.
   c. System computes `expectedMonthlyBilling = snapshotClientHourlyRate × (2080 / 12)`.
   d. System computes `creditAmount = round(expectedMonthlyBilling × snapshotVacationReservePercent / 100, 2)`.
   e. If the member's financials were first configured mid-month, the credit is pro-rated based on working days from configuration date to end of billing month.
   f. System creates a `credit` transaction with `IsAutoGenerated = true`, `BillingPeriodMonth` and `BillingPeriodYear` set, `CreatedByAccountId = null`, and description "{MonthName} {Year} accrual".
3. Members without financials or removed members are silently skipped.

### Flow: Admin triggers manual accrual

1. Admin sends `POST /api/admin/accrual/run` with `{ "month": 6, "year": 2025 }`.
2. System runs the same accrual logic as the background job for the specified billing month.
3. System returns a summary: `{ "processed": 5, "creditsCreated": 3, "skipped": 2 }`.
4. Admin opens a member's Vacation tab and verifies the credit transaction and updated balance.

### POST /api/admin/accrual/run

**Authentication:** required. Caller must be `admin` with `active` membership in at least one organization.

**Request:**
```json
{
  "month": 6,
  "year": 2025
}
```

- `month`: integer 1–12. Required.
- `year`: integer. Required. Must be the current year or earlier (cannot run accrual for future months).
- The endpoint runs accrual for all organizations the admin belongs to.

**Success `200`:**
```json
{
  "success": true,
  "billingPeriod": "June 2025",
  "processed": 5,
  "creditsCreated": 3,
  "skipped": 2
}
```

- `processed`: total active members with configured financials.
- `creditsCreated`: members that received a new credit transaction.
- `skipped`: members that already had a credit for this billing period (idempotency).

**Errors:**
- `400 Bad Request` (invalid month): `{ "error": "invalid_month", "message": "Month must be between 1 and 12" }`
- `400 Bad Request` (future month): `{ "error": "future_period", "message": "Cannot run accrual for a future billing period" }`
- `403 Forbidden`: caller is not `admin` — `{ "error": "forbidden", "message": "Only admins can trigger manual accrual" }`

## Vacation Formula Reference

```
Constants: 260 working days/year, 2080 billable hours/year (8h × 260d)

dailySalary         = monthlySalary × 12 / 260
expectedMonthlyBilling = clientHourlyRate × (2080 / 12)
creditAmount        = round(expectedMonthlyBilling × reservePercent / 100, 2)

reserveBalance      = SUM(transactions in current year)
availableDays       = min(floor(reserveBalance / dailySalary),
                         vacationDaysPerYear − usedDays)
                      floor at 0
```

## Out of Scope

- Manual credit entry (credits are auto-generated monthly by the system).
- Vacation requests — submit, review, cancel (spec 09).
- Organization Requests page (spec 10).
- Public holiday calendar (working days = weekdays only).
- Carry-over of unused days across years.
- Half-day or partial-day vacation.
- Currency conversion or multi-currency support within one member.
- Pagination on the transactions table.
- Integration with external payroll or billing systems.

## Test Cases

### TC-08-UNIT-01: Auto-accrual credit calculation

- **Level:** Unit
- **Preconditions:** none.
- **Steps:**
  1. Full month: clientHourlyRate=40, vacationReservePercent=3.33. Calculate credit.
  2. Full month: clientHourlyRate=60, vacationReservePercent=5.00. Calculate credit.
  3. Pro-rated: clientHourlyRate=40, vacationReservePercent=3.33, billing month has 22 working days, financials configured on day with 10 working days remaining. Calculate credit.
- **Expected Result:**
  1. expectedMonthlyBilling = 40 × 2080/12 = 6933.33. credit = 6933.33 × 3.33 / 100 = **230.88**.
  2. expectedMonthlyBilling = 60 × 2080/12 = 10400.00. credit = 10400.00 × 5.00 / 100 = **520.00**.
  3. fullCredit = 230.88. prorated = round(230.88 × 10/22, 2) = **104.95**.

### TC-08-UNIT-02: Available days calculation

- **Level:** Unit
- **Preconditions:** none.
- **Steps:**
  1. reserveBalance=1661.54, dailySalary=138.46, vacationDaysPerYear=20, usedDays=0. Calculate availableDays.
  2. reserveBalance=0, dailySalary=138.46, vacationDaysPerYear=20, usedDays=0. Calculate availableDays.
  3. reserveBalance=2769.23, dailySalary=138.46, vacationDaysPerYear=20, usedDays=18. Calculate availableDays.
  4. reserveBalance=-100, dailySalary=138.46, vacationDaysPerYear=20, usedDays=0. Calculate availableDays.
- **Expected Result:**
  1. floor(1661.54/138.46) = 12. Cap: min(12, 20−0) = 12. **availableDays = 12**.
  2. floor(0/138.46) = 0. **availableDays = 0**.
  3. floor(2769.23/138.46) = 20. Cap: min(20, 20−18) = 2. **availableDays = 2** (capped by annual limit).
  4. floor(-100/138.46) = negative → floor at 0. **availableDays = 0**.
